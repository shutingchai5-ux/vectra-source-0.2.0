# VECTRA

**园区与承运商（贸易公司）联合运营分析 · v2.0.0**

园区端与企业端分别部署。所有企业共用一个访问端口，通过不同账号登录确定所属公司，资料按公司分区保存。园区使用自然语言发起联合分析，三家企业在各自服务内处理本方资料，通过秘密共享形成联合指标，由多 Agent 协作解释证据、生成签名报告。

[GitHub 仓库](https://github.com/shutingchai5-ux/vectra-source-0.2.0) · [分端部署](docs/deployment.md) · [业务使用说明](docs/operations.md) · [经营台账说明](docs/business.md) · [八阶段流程](project_document.md)

## 1. 获取与首次准备

安装 Git、Bun 1.4.3 或更新版本，在团队当前的 v2.0.0 分支协作。命令均在包含 package.json 的目录执行。

~~~powershell
git clone https://github.com/shutingchai5-ux/vectra-source-0.2.0.git
Set-Location vectra-source-0.2.0
git switch v2.0.0
bun install
bun run build
bun run deploy:init
~~~

初始化会生成园区端、企业统一入口，以及三家公司各自的数据与密钥分区。已有 runtime-ts 时，必须先停止旧服务；初始化会迁移当前车辆、车次、预约计划，保留对话、报告、审计、Agent 模型配置和主智能体长期记忆。旧目录保留作迁移归档，日常启动不再读取它。重复初始化不会覆盖已建部署或重置密码。

园区账号在 runtime-deploy/park/first-login.json；三家公司的账号分别在 runtime-deploy/carrier-a、carrier-b、carrier-c 下的 first-login.json。企业账号均在同一个企业端地址登录；不要把密码、数据库或密钥发到 GitHub。初始化命令仅显示文件位置，不输出密码。

## 2. 启动两个端

园区端和企业端分别打开终端启动：

~~~powershell
bun run start:park
bun run start:carrier
~~~

| 入口 | 默认地址 | 操作职责 |
|---|---|---|
| 园区端 | http://127.0.0.1:8000 | 公共设置与容量、园区车辆概览、AI 联合分析、Agent 配置、报告与审计 |
| 企业端 | http://127.0.0.1:8101 | 使用本公司账号登录，维护本方车辆、车次、预约与经营台账 |

默认企业账号为 carrier-a、carrier-b、carrier-c，各自密码不同。账号固定绑定公司，不提供切换公司按钮；企业范围由服务端会话决定，修改网址、请求正文或角色凭据不能访问其他公司的资料。切换公司时先退出，再使用另一账号登录。同一浏览器的其他标签页检测到账号变化后会停止接受新账号的数据，提示重新登录或刷新。

**开发热更新**：园区运行 bun run dev park，企业端运行 bun run dev companies；一次启动两端运行 bun run dev:all。开发与正常启动共用入口：园区8000、企业8101，均读取对应 deployment.json 的 port。Vue 修改即时生效，Bun 监听后端源码重启；资料保留。修改部署配置后手动重启。开发与正常服务使用相同数据目录，不能重复启动。

默认地址用于本机联调。分别部署到园区和企业两个服务器时，见[分端部署说明](docs/deployment.md)。企业端口统一，三方计算仍有内部 TLS 协作端点，这些端点不是企业用户的页面入口。

## 3. 配置 Agent

登录园区端，打开左侧 **Agent 工作组**，分别在三个 Agent 的详情中配置底层 LLM：

- 园区协调 Agent：理解请求、委派与复核交付，仅它具有长期记忆。
- 统计规划 Agent：选择资料类型、入口、时间及受控指标。
- 运营分析 Agent：根据批准结果和真实证据解释事实、建议与边界。

三个 Agent 均须显式配置模型地址、名称、API Key 和接口格式，支持 Chat Completions 与 Responses，可选择深度思考方式。已保存配置默认只读，点击“修改配置”后编辑。保存不调用模型；首次提问会实际访问服务商。

企业协作节点负责本地数据和密码计算，不调用 LLM，不使用 Agent 后缀。不存在 demo 模式。

## 4. 企业准备资料

登录统一企业端的本公司账号，进入 **车辆与车次**：

1. **车辆档案**：选择车牌省份、字母，再填写剩余号码。车牌是唯一标识，每次手动添加一辆；可选车型、动力、额定载重。车辆档案不选择入口、不创建入园车次。已保存信息点击“修改车辆信息”后编辑。
2. **车次登记**：填写车辆及实际入口等完整信息，再确认“排队待入园”或直接确认入园。后续依次确认入园、开始作业、结束作业、离园；默认使用确认时的上海时间，同一车次沿用原入口。离园记录仅办理离园，里程与电耗按需补充。
3. **预约需求与运力**：按入口和半小时申报未来到园需求、可投入车次和预计作业量。零需求明确填零，缺报不会自动当作零。保存计划不会生成实际车次。

进入 **私有经营台账**，按需维护第一批全部扩展资料：

| 台账 | 可以支持的联合信息 |
|---|---|
| 运输需求与到达弹性 | 未预约车次、紧迫需求、最低保留、可调整及可提前/延后规模、需求作业量、货量 |
| 实际装载与空驶 | 重量/体积/托盘总量、同批记录加权利用率、低装载比例、载货与空驶里程、联合空驶率 |
| 回程运力 | 按粗区域和开始时段汇总可利用回程车次额度 |
| 分时充电需求 | 本地由电池与电量派生的需求电量、接口分类、短时限与已知功率下仍无法完成的请求 |

四类台账支持逐条录入、JSON 导入草稿、资料完整范围声明与历史版本。装载事实必须关联本公司已离园车次；充电请求必须关联本公司已建档车辆，禁止同车重叠申报。完整范围内空台账可以表示明确为零；可选字段缺失仍保持未知。详细字段和边界见[经营台账说明](docs/business.md)。

## 5. 园区发起分析

园区维护公共名称、固定的东南西北四个入口，以及各时段接纳、作业和充电容量。打开 **联合运营分析** 选择场景、入口及上海时间范围，点击“带入 AI 对话”，核对问题后发送；也可使用新对话输入框上方的“猜你想问”。

| 场景 | 可直接修改的提问示例 |
|---|---|
| 入口运行 | 统计东入口今天到达的车次数、车辆数、未离园车次数和平均排队时长。 |
| 完整链路瓶颈 | 分析东入口今天到达车次的跨企业等待与周转瓶颈，说明共同完整样本。 |
| 预约运力 | 统计东入口未来两小时的预约需求与运力计划，按30分钟分组并给出人工错峰建议。 |
| 需求弹性 | 统计东入口未来六小时的运输需求与到达弹性，按120分钟分组，比较未预约车次、最低保留和可调整车次。 |
| 装载空驶 | 统计东入口昨天已离园车次的载重加权装载利用率、载重利用率低于50%的记录比例和联合空驶率。 |
| 回程机会 | 统计东入口未来六小时仅华东粗区域的可利用回程车次，按120分钟分组并说明资料范围。 |
| 充电压力 | 统计东入口明天的分时充电需求，按120分钟分组，比较接口电量、紧迫请求与园区充电容量。 |

单次时间跨度最多31天；实绩不能在未来，未来申报最多提前31天。经营统计最多20项指标，未来分组最多128组且受计算向量总量限制。装载比值使用同批完整记录，不能平均各家公司比例。可提前和可延后的需求可能重叠，不能相加。完整半小时时段、三家资料声明与容量均齐全时才计算充电电量缺口；总量充足仍不等于逐车排程可行。

## 6. 阅读结果与排错

每条角色消息标注八阶段之一：**请求受理 → 查询规划 → 签名授权 → 节点准备 → 份额交换 → 输出重构 → 证据分析 → 报告交付**。卡片用上海真实时间说明当前操作、原因与后续动作，安全协议注明全称与用途，可查看公开证书、任务与结果签名。独立园区端不提供企业私钥、原始台账或输入份额材料。

对话和 **签名报告** 共同展示业务结果、资料覆盖与有效记录。只有任务“已完成”才表示所需统计、分析和签名报告交付；模型建议仍需人工确认。报告可下载、验签，修改内容后验证应失败。**证据与审计** 按数据、任务、安全、计算、报告和系统事件分类。

左侧保存对话历史。删除对话会停止关联任务、移除应用中的对话与报告，**不改变长期记忆**；已有审计与 Git 日志继续保留。

| 现象 | 处理方法 |
|---|---|
| 企业无法连接 | 确认三家企业服务在线，核对协作地址、端口与证书；离线时不会伪造联合结果 |
| 查不到实绩 | 核对实际数据日期、入口及到达/离园口径 |
| 资料待补齐 | 各企业核对并保存资料完整范围，未知值保持空缺 |
| 充电缺口未知 | 核对三家完整声明、半小时边界及相应接口容量是否齐全 |
| 模型失败 | 到对应 Agent 检查实际接口格式、服务地址与凭据，结合原始状态码排查 |
| 保存冲突 | 刷新当前版本核对后重试，草稿不会自动覆盖其他修改 |

模型单次响应默认120秒，整轮协作默认600秒，可在 .env 中分别修改 VECTRA_MODEL_TIMEOUT、VECTRA_TASK_TIMEOUT 后重启。

## GitHub 协作与实现边界

通过 Issue 描述问题，功能分支提交 Pull Request。提交前运行 bun run check；修改统计、安全或存储时运行相关检查。无需为文案反复运行完整测试或进行浏览器检查。技术栈为 **Vue 3 + TypeScript + Effect + Vite + Element Plus，Bun + TypeScript + SQLite**；模型负责规划与解释，代码控制权限、统计与密码协议。

只提交本次源码、文档、依赖锁文件和审核后的脱敏应用日志。logs/park、logs/companies、logs/carrier-a、logs/carrier-b、logs/carrier-c 分开记录各端日志并纳入 Git；runtime-deploy、归档运行数据、密码与私钥不提交。Codex 辅助文件放在仓库外的同级 codex_files。

当前支持园区/企业两个服务、账号隔离与公司密钥分区，尚未完成现场跨主机网络、真实车辆采集或外部模型稳定性验收。Shamir 使用一次多项式，数学重构门限为2，执行要求三家全员参与；线性一致性检查不构成恶意安全证明，公开联合结果也可能被推断。签名只证明来源与完整性。自动预约、私密分配、逐订单撮合、逐车充电排程与更强安全协议仍属于后续工作。

企业统一服务承载三家公司计算上下文和分区密钥，账号隔离不等于三家组织独立控制主机；宿主机管理员仍可访问本机文件和进程。部署和协议边界见分端部署说明。
