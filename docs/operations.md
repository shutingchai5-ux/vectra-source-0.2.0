# 跨企业瓶颈分析与预约运力协同

以下两个场景及[第一批经营扩展](business.md)都通过主、子 Agent 委派、三家承运商秘密分享计算、证据分析和签名报告流程执行。侧栏的“联合运营分析”用于准备问题与维护园区容量；点击“带入 AI 对话”只填入问题，确认发送后才开始任务。

## 跨企业等待与周转瓶颈

先在“承运商工作台 → 车次登记”录入实际记录。确认入园前可以展开“补充跨企业链路、预约与排队信息”；已保存车次可在“全部记录 → 查看或更正历史信息”补充真实时间。日常生命周期仍为入园、开始作业、结束作业、离园。

| 环节 | 起点 | 终点 |
|---|---|---|
| 承运商待发 | 备车就绪 | 运输发车 |
| 运输在途 | 运输发车 | 到达园外集结点 |
| 园外等候 | 到达园外集结点 | 到达入口队列 |
| 入口排队 | 到达入口队列 | 开始入园核验 |
| 入园核验 | 开始核验 | 入园 |
| 园内转运 | 入园 | 到达作业等候区 |
| 待作业 | 到达作业等候区 | 开始作业 |
| 实际作业 | 开始作业 | 结束作业 |
| 作业后待离园 | 结束作业 | 离园 |

未知时间留空，不补零，不以当前时间替代未知事件。实际时间必须按顺序、不能在未来；从本次最早事件到最后事件最多31天。旧车次保留原记录，不推算缺失的企业侧时间。

在“联合运营分析 → 跨企业瓶颈分析”选择入口和实际到达区间，或直接提问：

> 分析东入口今天到达车次的跨企业等待与周转瓶颈，比较各环节耗时并说明完整链路覆盖。

结果对每个入口显示两套信息：

- **已有记录观察值**：该环节端点齐全的车次均值及有效车次数。不同环节的样本可能不同。
- **完整链路共同样本**：九个环节端点全部齐全的同一批车次，用于比较均值、占比和耗时排名；端到端从备车就绪到离园。

没有共同样本时，系统仍展示已有观察值和缺失情况，暂不给出瓶颈排名。运输在途包含必要行程，最长耗时只是复核线索，不直接证明责任、因果或可消除的浪费。规划由后端补齐固定20项统计，仍在一次三方协议中执行。

## 未来预约需求与运力协同

### 1. 各承运商填报本方计划

在统一企业入口登录本公司账号，在“车辆与车次”进入“预约需求与运力”。每个入口、每个半小时填一行：

| 内容 | 含义 |
|---|---|
| 预计到园车次 | 本方预计在该时段安排到园的运输需求 |
| 可投入运输车次 | 本方分配给此入口时段、可承接运输的车次额度 |
| 预计作业量 | 对应预计到园需求的总作业分钟数 |

运力是车次额度，不是去重车辆数。同一批运力不要重复承诺给不同入口。零需求要显式填零，且预计作业量为零；有需求时预计作业量必须大于零。

可连续添加1—48个半小时时段到草稿，再逐行修改并保存，也可导入JSON数组追加到草稿。系统只允许维护当前承运商，保留其他承运商内容；同一入口时段不能重复。本公司页签切换保留草稿，企业端不允许切换其他公司。

### 2. 园区维护容量

在“联合运营分析 → 预约需求与运力协同”下方填写“园区时段容量”：

- **入口接纳额度**：该半小时可接纳的车次数。
- **可用作业量**：分配给该入口时段的总作业分钟数。例如三个作业位各可提供30分钟，总量为90分钟。

共享作业资源应先分配到各入口，避免重复计入。零容量表示明确不接纳；没有配置保持未知，不能当作零或无限。

### 3. 发起联合分析

选择入口、起止时间及分组粒度，点击“带入 AI 对话”并确认发送，也可提问：

> 统计东入口未来两小时的预约需求与运力计划，按30分钟分组，核对入口及作业资源，给出错峰建议。

> 统计东入口、南入口明天的预约需求与运力计划，按60分钟分组，指出需要人工协调的时段。

预约使用独立数据类型，允许查询至当前时刻后31天，区间跨度最多31天。上海时间统一显示。“今天”的预约协同表示剩余时段，“明天”为完整上海自然日。历史实际车次继续禁止未来时间。

原始申报粒度固定30分钟，结果可按30、60、120、240、720或1440分钟分组。按计划时段开始时间执行含起点、不含终点选择，边界时段不拆分折算。每次最多128个入口时段、2048个分享分量；范围过大时应增大粒度或减少入口。

### 4. 读取结果与协调建议

三家协作节点各自读取自己的冻结计划，分享需求、运输额度和作业量的统计分量，同时计算申报覆盖。中心核对签名结果后，与本轮冻结的园区容量比较。

只有每个基础半小时时段三家都显式申报、且容量配置完整，才给出建议安排数。它取需求、运输额度、入口额度、按平均作业量估算的作业资源约束中的最小值。作业资源判断只是总量估算，不能代替逐车资源排程。

缺报或缺容量的时段显示“待补齐资料”，保留已经收到的汇总数据。错峰建议仅使用查询范围内、同一入口的后续可用时段，并逐次扣减目标额度，避免多个建议重复占用相同资源。

**建议不会自动改写预约，也不会生成实际入园车次。**承运商与园区确认调整后，可手工更新尚未开始的计划。已经开始的时段禁止修改，不把原计划改写为实际发生。

时段结束后，可以点击“归档已结束时段”，核对草稿后保存，释放当前台账额度。归档保留原始版本和既有签名报告。通过“查看台账版本”可只读查看最近50个版本，承运商始终只能读取本方历史；更早报告仍按冻结版本复验。历史快照不能添加、修改、导入或保存，点击“返回当前台账”继续维护未来计划。

## 数据、报告与排查

每次保存发布新版本；已签名任务冻结计划、园区名称及汇总容量，后续修改不改变旧报告。历史报告继续可下载、验签，对话中注明实际统计与申报计划的区别。主智能体长期记忆记录计划属性，不把历史预约结果当成实际到园。

“证据与审计”将预约申报与容量更新归入数据管理。Git诊断日志继续脱敏，不记录各方原始时段数组、企业侧事件时间、密钥或完整份额。

当前园区端与企业端分别部署，企业通过同端口的不同账号区分，本公司账号只可读取本方资料，密钥在企业服务内分目录保管。园区委派已签名任务，各方通过跨服务双向 TLS 交换份额，园区收到批准联合结果。具体网络与迁移步骤见[分端部署](deployment.md)。本机跨服务验证不等于现场跨主机或采集真实性验收。

接口：本方计划使用 `GET/PUT /api/carrier/reservations`，读取公开目录与容量使用 `GET /api/reservations`，容量保存使用 `PUT /api/reservations/capacity`。对应的 `/versions` 接口列出最近50个版本，读取接口可携带 `?version=<版本>` 查看历史，仍按本方角色限制。写入绑定当前版本；过期本方内容拒绝覆盖，其他承运商更新可安全合并。
