# 园区端与企业统一入口

园区端和企业端分别部署。企业端共用一个页面/API端口，通过不同账号登录区分公司；没有按公司切换端口的使用方式。

## 默认入口与账号

| 服务 | 正常入口 | 开发入口 | 启动命令 |
|---|---|---|---|
| 园区端 | http://127.0.0.1:8000 | http://127.0.0.1:8000 | bun run start:park / bun run dev park |
| 企业端 | http://127.0.0.1:8101 | http://127.0.0.1:8101 | bun run start:carrier / bun run dev companies |

两种模式的公开端口均以各自 deployment.json 的 port 为准，不再单独设置 VECTRA_WEB_PORT。开发模式由 Vite 提供公开页面、热更新和同源 /api 代理，Bun 后端仅监听回环地址上的内部端口，默认在公开端口基础上加10000（超过65535时减10000），即18000、18101。内部端口冲突时，可在单端启动前设置 VECTRA_DEV_API_PORT；它不改变用户访问地址。bun run dev:server 与 bun run dev:web 分开运行时也使用同一组配置。

企业 A/B/C 的默认账号分别为 carrier-a、carrier-b、carrier-c，密码各不相同。密码与账号保存在各公司目录 first-login.json，园区在 park/first-login.json。登录后公司固定绑定会话，不能通过 carrierId、角色头或历史版本编号改成其他公司。切换账号先退出，再登录。

## 初始化与旧配置升级

全新使用先 bun install、bun run build、bun run deploy:init。已有旧服务时先关闭开发监听，或 bun run stop --all；旧单体服务使用 bun run stop --legacy。初始化默认从已停止的 runtime-ts 迁移，来源可用 --legacy 指定，目标默认 runtime-deploy，可用 --root 指定。

如果已生成上一版三个企业页面端口，再次执行 deploy:init 会补齐 companies/deployment.json，统一企业公开地址，不重置公司密码，不删除车辆、车次、台账或历史版本。正常使用只启动园区和企业两个服务，原8102/8103页面服务不再启动。

目录分工：

- park：园区数据库、对话、报告、审计、Agent 配置、仅主智能体长期记忆及园区私钥。
- companies：统一入口配置、企业账号与公司绑定、登录会话数据库和运行锁。
- carrier-a/b/c：各公司的车辆、车次、预约、经营台账、计算身份私钥及独立加密版本。

企业统一服务根据已验证的账号绑定选择公司上下文，三个上下文不单独启动HTTP页面服务。三方分别使用自己的签名、TLS和输入密钥，并保留三方秘密共享过程。它们在同一企业服务进程内运行；这属于账号与数据分区隔离，不是三家组织独立掌控宿主机的安全边界。

首次迁移读取旧目录，认证解密并按公司重新加密当前车次、车辆、预约计划；园区保留 SQLite 对话、报告、审计、Agent 运行和长期记忆，保留模型配置。园区报告身份和存储密钥保留，旧外层报告仍可验签；企业身份重新签发，旧企业报文按退役身份理解，不能冒充新部署执行。

旧 runtime-ts 仅作归档，不再运行或分发。初始化重复执行不会覆盖已有业务资料或重置密码，已经存在的统一入口配置由部署管理员维护。

## 配置两个服务器

园区主机只部署源码和 park 目录；企业主机部署相同源码、companies及三家公司分区。分别 bun install、bun run build；运行目录不进入 GitHub。园区与企业主机可不同，企业浏览器用户仍访问同一域名和端口。

园区使用 park/deployment.json，企业使用 companies/deployment.json。设置 host、port、publicUrl（正式域名使用HTTPS），企业配置还包含 parkUrl 和三家分区配置路径。dataDir 与 logDir 相对于各自配置文件解析。设置 VECTRA_DEPLOYMENT_FILE 为本端配置文件绝对路径，可将源码与运行目录分开。

三家公司分区配置中的身份、私钥与本地台账目录保持独立，publicUrl/publicPeers 使用相同企业公开入口。park.publicPeers 也指向这个入口，园区页面只显示一个“企业端”链接。修改公司名称仍由园区公共设置统一维护，账号绑定不随显示名称改变。

内部协作端点默认园区8500，企业三个计算身份8501、8502、8503。federation.peers 使用 tls://实际主机:端口；协议为 TLS 1.3 双向认证与签名 JSON 行 RPC，**不是HTTP**。跨主机时，企业三个身份均指向企业服务器的相应内部端口，园区身份指向园区服务器；防火墙仅对协作主机放行，不作为用户页面入口。普通网页反向代理只转发园区或企业的HTTP端口，内部TLS采用直连或四层透传。

运行服务后不要改写分区私钥或手工交换公司目录。正式HTTPS可以在反向代理终止；远程普通HTTP登录配置会拒绝。保持主机时钟同步，业务显示为Asia/Shanghai。

## 登录与权限

账号密码使用Argon2id，12小时登录会话只存令牌摘要。企业统一Cookie为HttpOnly、SameSite=Strict，HTTPS使用Secure。企业账号在服务端持久绑定公司，不能由客户端改绑。API还检查同源和本方操作凭据。

同一浏览器共享企业登录Cookie；若另一个标签页切换账号，旧页接到不同公司标识时停止接纳响应，提示刷新或重新登录，避免把新公司资料放入旧公司草稿。不同浏览器或隔离浏览器环境可以并行使用不同账号。

每家公司只能维护本方档案、车次、预约和经营数据；读取旧版本仍限定本公司。园区可读取另行授权的公开档案与车辆状态概览，不能读取私有经营台账、私钥或输入份额。实际控制服务器的管理员仍有宿主机访问能力，不能用网页账号隔离声称抵抗管理员或进程内窥探。

## 停止、热更新与日志

正常服务使用 bun run stop park、bun run stop companies 或 bun run stop --all。企业停止时会关闭三方计算上下文并释放分区锁。开发使用 bun run dev:all 同时启动两端的Vue HMR与Bun watch；Ctrl+C停止监听。开发和正常服务不能同时使用同一分区。

logs/companies记录统一入口登录和HTTP错误，logs/carrier-a/b/c分别记录本方业务与计算事件，logs/park保存园区对话和操作日志。日志均脱敏并按项目要求纳入Git；凭据、原始台账、密钥、数据库和构建不提交。

当前隔离检查覆盖同端口三账号、跨公司写入/角色/历史版本拒绝，以及真实mTLS、Shamir、Agent夹具和报告签名。检查运行在本机，不能代替跨主机、反向代理、外部模型、现场数据或恶意安全验收。一次多项式数学门限为2，当前执行仍要求三家全部参与；共享服务器不提供独立组织之间的非串通保证。
